# Phase 3 synthetic operations foundation

**Status:** The provider-free contract tranche is implemented and locally verifiable with disposable synthetic state; Phase 3 overall remains partial until the Phase 3B evidence plan passes. This tranche is not production authentication, real recovery, a production database, malware scanning, sandboxed conversion, hosted or self-hosted deployment, personal-data acceptance, Guardian authority, Release, or v1 readiness.

## Deep ownership boundaries

- `packages/domain` remains the only authority for Contingency Plan lifecycle decisions, and still stops at Concern.
- `packages/identity` issues and verifies canonical session facts. `packages/application` accepts only a session identifier and ignores caller-supplied principal or time fields.
- `packages/operations` owns encryption serialization, retention, durable-work state, leases, fencing, snapshots, and restore-safe enforcement. A worker executes an application decision; it does not recreate domain rules.
- `packages/documents` owns quarantine and inspection-evidence validation. Scanner and converter adapters cannot approve structurally forged evidence.
- `apps/web` uses an explicitly synthetic session verifier and synthetic fixture inspection so the runnable browser surface remains honest about what is absent.

## Security semantics demonstrated locally

An interactive request is still an explicit `POST` with application-level user-presence intent. The application resolves its Owner and authentication times only through `SessionVerifier`; unknown, expired, revoked, different-revision, or malformed sessions fail before a transaction. In the production target, a deliberate UI action is not itself a fresh WebAuthn ceremony: sensitive lifecycle or identity changes require a newly verified assertion, while ordinary mutations also require CSRF protection.

Operations use at-least-once semantics. A task can be replayed after an external sink accepts it but before acknowledgement, so future sinks must deduplicate by opaque task identity. Fencing guarantees only that an expired or superseded worker cannot later commit database state. Restore-safe mode permits inspection and snapshot restoration but rejects metadata mutations, claims, and dispatch.
