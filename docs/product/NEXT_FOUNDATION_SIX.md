# Next six foundation slices

**Status:** Implemented and locally verified as a Phase 2 synthetic foundation. This is not evidence that an account system, production database, durable personal-content storage, encryption, malware scanner, Guardian authority, hosted service, or Release exists.

These slices follow the roadmap rule that authentication and persistence boundaries must be decided before Vidha accepts real data. Each slice must remain usable with disposable synthetic fixtures until its security and retention contract is accepted.

| Order | Bounded slice                                | Intended outcome                                                                                                                                                                                   | Required evidence and stop condition                                                                                                                                                                                               |
| ----- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | Authentication command boundary              | Define a provider-neutral authenticated-principal and recent-auth command contract, including a navigation-only reminder challenge that cannot mutate state through `GET`, preview, or email open. | Exact authorization matrix, scanner/prefetch tests, expiry/replay tests, and one accepted ADR if the provider or credential model becomes hard to reverse. Stop before real accounts or recovery enrollment.                       |
| 2     | Persistence portability prototype boundary   | Compare one SQLite-compatible model with one PostgreSQL model, then define narrow repository and transaction ports around the existing domain without selecting the production database.           | Current official-source comparison, concurrency/uniqueness prototype, migration parity test, backup/restore constraints, and an ADR only after a real trade-off is resolved. Stop before storing personal content.                 |
| 3     | Application authorization seam               | Add an application layer that maps authenticated commands to domain decisions without recreating time or safety rules in routes, schedulers, or providers.                                         | Owner/Guardian/Recipient/operator denial matrix using synthetic identities, injected clock tests, and no framework import in `packages/domain`. Stop before Guardian Attestation semantics.                                        |
| 4     | Append-only audit and idempotency store      | Persist accepted domain events and processed semantic command keys transactionally using disposable data.                                                                                          | Duplicate command, concurrent writer, crash/retry, ordering, and restore-safe tests; logs must exclude content, contact data, filenames, and tokens. | 6     | Untrusted import intake seam                 | Separate file classification, limits, source preservation, quarantine state, and conversion approval from the current temporary text editor.                                                       | Adversarial TXT/Markdown fixtures, detected-versus-declared type tests, resource limits, and a provider-neutral scanner/converter port. Keep HTML, DOCX, archives, and active content unconvertible until sandbox evidence exists. |

## Boundary after these six

These completed synthetic slices establish safer foundations for later durable workflows. They do not resolve Guardian/Recipient role overlap, Guardian Attestation wording or quorum, Veto Window evidence, Delivery Hold authority, Automatic Fallback timing, Standard Mode key custody, Sealed Mode, provider delivery, hosted operations, or Release. Those remain separate user-decision and release-readiness gates.
