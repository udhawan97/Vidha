# Phase 3G update-safe local rehearsal

**Status:** Six bounded source slices are implemented locally; exact-commit CI acceptance remains required. This phase protects a synthetic in-memory browser rehearsal from accidental reload and makes service-worker update loss explicit. It is not durable storage, autosave, encrypted persistence, a supported-browser update guarantee, deployment, or release authority.

Phase 3G closes the next user-visible continuity gap after Phase 3F. The PWA could announce a waiting build, but **Update now** reloaded the app without knowing whether the Owner had changed the synthetic Plan, Editable Documents, imports, Attachments, or Document Versions. The previous copy advised the Owner not to update while editing but did not enforce or explain the consequence.

| Order | Bounded slice                    | Implemented outcome                                                                                                                                                                      | Evidence and stop condition                                                                                                                                                                                                                                          |
| ----- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | Accepted session-work signal     | Successful Plan actions plus accepted or staged document/import/Attachment/Document Version work mark the current browser rehearsal as changed                                           | App and component tests prove untouched state remains reloadable and document work activates the marker. The signal is deliberately conservative and is not a canonical dirty-state digest, audit record, or persistence contract                                    |
| 2     | Accidental-reload protection     | A changed rehearsal installs a scoped `beforeunload` guard; untouched state and an explicitly confirmed update do not                                                                    | Unit tests exercise the browser event before work, after work, after confirmation, and after update failure. Stop before claiming unsaved work can be recovered, that every browser displays identical native wording, or that abrupt process/device loss is covered |
| 3     | Explicit update consequence      | A waiting build presents **Review update** and names the complete in-memory state that **Update and clear session** will discard                                                         | The reversible **Keep working** action receives focus first; Escape closes the native dialog and focus returns. Stop before background update, migration, rollback, or installed-app claims                                                                          |
| 4     | Owner-action serialization       | A service-worker update cannot start while a synthetic Owner action is settling                                                                                                          | The update control is disabled with a concrete waiting label and explanation. This reuses the browser action boundary only; it is not a server lock, multi-tab coordination, or service-worker transaction                                                           |
| 5     | Failure-safe update retry        | A rejected update keeps the confirmation open, restores reload protection, and explains that the rehearsal remains available                                                             | Component tests force rejection and prove the update can be retried or canceled. Stop before bad-service-worker recovery, cache rollback, offline data migration, telemetry, or production updater claims                                                            |
| 6     | Honest responsive update journey | The existing editorial update card now distinguishes untouched, changed, pending-action, updating, offline-ready, and failure states while reusing the safe native confirmation boundary | Exact-commit component, type, lint, build, documentation, accessibility, and desktop/mobile WebKit checks remain mandatory. Final install/update acceptance still requires real supported-browser and installed-PWA evidence; WebKit is not Safari                   |

## Gate after Phase 3G

Exact-commit local and CI checks must pass, including the existing Phase 3B disposable PostgreSQL, WebAuthn, backup, scheduler, and rootless-import rehearsals plus the Phase 3C–3F browser and document boundaries. Passing proves only that this synthetic tab warns before common reload paths and requires an explicit decision before applying a waiting service-worker build. It does not preserve or migrate the rehearsal, recover from browser or device loss, prove installability or update behavior in a supported browser, authorize real identities or content, or enable Standard Mode, Sealed Mode, providers, Guardian Attestations, Veto Window, Delivery Hold, Automatic Fallback, Release, deployment, a tag, or a GitHub release. Every checkbox in sections 1–11 of `docs/release/V1_RELEASE_GATES.md` remains evidence-gated.
