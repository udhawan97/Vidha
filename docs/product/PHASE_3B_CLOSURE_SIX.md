Slice 1 uses only a run-sentinel-owned PostgreSQL database, run-unique content-free job/audit rows, a run-unique digest-pinned Compose fixture, and a tmpfs database root. Its migration and claim probes terminate identity-checked PostgreSQL backends, distinguish pre-commit rollback from post-commit lost acknowledgement, and retry with checksum/idempotency and fencing checks. Its worker-partition fixture uses a five-second client query-read timeout so a severed half-open socket reaches the bounded recovery path; that fixture value is not a production latency policy. The gate drops only its sentinel-owned rehearsal database, deletes only its generated capacity rows, removes its Compose project, restarts PostgreSQL without the application schema, and tears it down again. A passing exact-commit gate proves this bounded disposable behavior; it is not failover, high availability, general outage recovery, a production capacity claim, or persistent-volume evidence.

Slice 2 rewraps every selected metadata data key and writes one immutable rotation report in the same PostgreSQL transaction. Its lost-ack replay returns the committed report; conflicting reuse fails closed. The backup gate runs PostgreSQL 18 `pg_dump` and `pg_restore` from the digest-pinned image, excludes live runtime mode from the archive, wraps the custom archive behind the injected key-provider contract, signs two generations, advances an external file inventory only after artifact persistence, rejects a truncated archive and prior-generation rollback, restores through a dedicated non-superuser role, inserts `restore_safe` before any application adapter starts, verifies portable snapshots and migration checksums, proves the read-only inspection role cannot promote, then requires one immutable invariant digest for explicit promotion. Retention rehearsal can retire only an exact non-current generation. This is still a disposable bounded archive held in memory during encryption, not streaming backup software, external KMS custody, a durable-volume recovery result, RPO/RTO evidence, or a Standard Mode claim.

Slice 3 adds an opt-in runtime route that is rejected unless the API binds to `127.0.0.1` and the configured public origin is an exact `http://localhost:<port>` origin. The disposable flow creates only a synthetic Owner Credential, uses browser WebAuthn APIs against the existing ceremony coordinator, hashes the Owner ID into a standards-bounded user handle, issues only an opaque digest-backed `__Host-` session cookie, rotates it atomically, derives a session-bound CSRF token server-side, and revokes or expires authority through the canonical identity coordinator. POST routes require exact Host and Origin, JSON, bounded bodies, and same-origin fetch metadata when present; GET cannot mutate identity state. The CI gate uses a Chromium CDP virtual authenticator for the full registration/authentication/replay/rotation/revocation path and uses Firefox and WebKit only for the transport and security-header boundary. That is not real-authenticator, Safari, supported-browser, identity-proofing, public-origin, or production-session evidence.

Slice 4 moves recovery proof acceptance, consumption, and cancellation behind one transactional identity-repository interface. The PostgreSQL adapter requires separate issuance events and rows for the saved-code and issued-channel factors, domain-separates their digests, accepts identical retries after a lost acknowledgement, rejects conflicting reuse, records pair-level accepted/consumed/cancelled state, commits per-factor and per-attempt failure counters without advancing the Owner security revision, and applies an Owner-wide exponentially increasing lock across distinct attempts. Recovery completion or cancellation shares the serialized identity transaction, so exactly one concurrent command can advance and the other fails on its stale revision; a rejected factor or new-credential registration leaves the accepted pair unconsumed and the Owner state unchanged. Schema migration 3 splits legacy paired rows, conservatively attributes any legacy pair failure count to both new factor rows, tombstones pre-contract unconsumed attempts, narrows the application role to immutable identity/digest fields and bounded mutable columns, and makes recorded terminal timestamps append-only. Current logical backups include accepted proof state; restore inspection cross-links every pending Owner recovery with exactly one accepted, nonterminal, same-Owner attempt, both factors, coherent pair/factor counters, and an expiry that covers the cooling-off boundary, while rejecting orphan active attempts. Restore-safe mode rejects identity and proof mutation, and explicit promotion is required before a still-controlled credential can cancel. The loopback rehearsal starts disabled, reloads credential/session state, remains disabled if hydration fails, and gives a concrete run-owned-cleanup path for a lost credential, while still exposing no recovery command, Verified Owner Channel delivery, email/SMS fallback, real factor, or real destination.

Slice 5 replaces the runtime worker's deliberate `advance_plan_stage` rejection with one deep PostgreSQL adapter. The worker claims and executes one job per poll and supplies only the opaque claimed-job and lease identifiers; the adapter reloads immutable intent, locks the Plan before the job, uses database time, reconstructs the schedule semantic from the current Plan and policy revision, and submits only a canonical `ADVANCE_TIME`. Accepted Plan state, processed-command history, append-only audit, next-stage allowed work, and current-job completion commit together. Four identity-checked backend terminations cover before decision, after decision, after writes, and post-commit lost acknowledgement. A historical-time fixture advances separately through Reminder, Overdue, and Concern, while a revision-drifted schedule fails closed as an inspectable dead letter. An orphaned Plan job exhausts its bounded retries, the existing synthetic sink replay covers a crash after acceptance, and runtime telemetry serializes only an allowlisted event, job kind, and failure code. Migration 4 grants the worker only the additional Plan/audit/outbox columns required by this transaction and deliberately denies audit-history reads. The task allowlist remains `advance_plan_stage` and `synthetic_notice`; no provider or state beyond Concern exists.
