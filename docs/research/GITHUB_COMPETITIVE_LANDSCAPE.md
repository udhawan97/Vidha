# GitHub and official-product landscape: sensitive document release

Competitive snapshot: 2026-08-16; Vidha naming addendum: 2026-08-20 (America/Chicago)

> **Repository interpretation:** this is a research snapshot, not the current product contract. Where the report says “per document,” Vidha's canonical model now uses one recipient-specific **Envelope** with one Protection Mode and one Release Policy covering every contained Editable Document and Attachment. `CONTEXT.md` and accepted ADRs control implementation terminology.

## Bottom line

The broad idea is **not unique**. Open-source dead-man switches, encrypted legacy boxes, password-vault emergency access, and hosted after-death planning products all exist.

Five comparisons are especially decision-relevant:

1. **[Letter Vault](https://github.com/SaiHtetWaiYan/letter-vault)** is the closest feature-shaped GitHub match: WYSIWYG letter sections, per-section recipients, attachments/media, and global/fixed-date/relative-delay modes; its M-of-N keyholder gate and forced fallback apply to the global-unlock path.
2. **[Afterword](https://github.com/Nxrnoob/Afterwords)** is the closest experimental object-model match: encrypted rich-text/files, item-level assignments, per-item dates, inactivity/grace release, and export—but its own roadmap and source show unfinished or unclear contracts.
3. **[Digital Legacy Protocol](https://github.com/Ciprian-LocalPulse/digital-legacy-protocol)** is the strongest protocol precedent: signed manifests with asset-level beneficiary, condition, action, and secret-share instructions, plus trustee quorum attestations, while explicitly disclaiming a finished hosted vault.
4. **[LastSignal](https://github.com/giovantenne/lastsignal)** is the strongest current encrypted-message comparison: self-hosting, client-side encrypted recipient messages, email check-ins, per-recipient delays, and an optional trusted-contact pause.
5. **[Everplans](https://www.everplans.com/)** is the closest hosted policy comparison: document organization, item-level recipient permissions, a human “unlocker,” an owner-denial window, and automatic unlock after that window.

This bounded review did **not** find one product that combines all of the proposed wedge:

- fully open-source and free to use;
- a maintained hosted default **and** an installable/self-hosted escape hatch;
- one-adult Owner rather than a family/team password manager;
- one workspace with rich-text/Markdown authoring **and editable document imports**;
- recipient-specific documents with independent per-document release, attestation, and evidence policies;
- a deliberate **Standard vs Sealed** confidentiality choice per document; and
- guardian attestation and evidence review as the normal release path, with a narrowly constrained automatic fallback.

That is a plausible product combination, not proof of novelty. Letter Vault means neither “rich posthumous letters” nor “M-of-N keyholder gating with a forced fallback at vault level” is a novelty claim. The honest position is a more rigorous **dual-privacy continuity document workspace**, not “the first dead-man switch.”

`Vidha` is also **not globally unused or legally cleared**: the exact GitHub account, several exact-name repositories, an established software-services company, and the `.com` and `.org` domains already exist. The owner-qualified `udhawan97/Vidha` repository path was available before this repository moved, and four major package registries returned no exact package, but those narrower facts do not establish exclusivity. Treat Vidha as provisional pending broader availability and appropriate legal review.

## Method and evidence boundary

- Sources are limited to GitHub repository/API metadata, repository README/source/license files, first-party product documentation, official package-registry endpoints, and direct endpoint/DNS availability checks.
- “Last push” is GitHub API `pushed_at`, not proof of a production release, security review, or healthy maintenance.
- Star counts are a volatile discovery signal, not a quality score; they are included only to distinguish established repositories from tiny experiments.
- This was a bounded search, not an exhaustive GitHub census, trademark search, patent search, or live security audit.
- Negative findings mean “not documented in the primary sources reviewed,” not “cannot exist anywhere in the product.”

## Recommended differentiation

Avoid positioning this as an “open-source dead-man switch,” “rich letters after death,” or simply “guardian-gated delivery.” Letter Vault, LastSignal, Digital Legacy Protocol, circa10a, Hereditas, ReMemory, and older scripts already occupy those ideas.

A sharper position is:

> **An open-source dual-privacy continuity document studio for one adult: import or write living instructions, choose Standard or Sealed per document, and give each document its own recipients and explicitly constrained release policy.**

Rank the product thesis rather than treating every feature as an equal novelty claim:

1. **Core wedge — the entire contract per document.** A medical instruction, pet-care sheet, private letter, and credential handoff should each own Standard/Sealed mode, recipients, attestation/evidence requirements, quorum, fallback permission, and timing rather than inheriting one vault-wide rule.
2. **Supporting differentiator — editable imports.** Provide rich authoring, revision history, DOCX/Markdown/text import into the editor, preview, original attachments, and recipient-ready reading packets rather than only letters or attachments.
3. **Trust baseline — release safety.** Test restore/delivery drills; pre-provision and verify recipient-key access; support guardian-collusion resistance, revocation, identity/channel-compromise response, multi-channel Owner cancellation, false-positive recovery, retention limits, staged notification, and tamper-evident, privacy-minimized audit events. Automatic fallback should be deliberately slow and opt-in per document; leave it off by default for Sealed documents.
4. **Distribution posture — free/open plus hosted and self-hosted.** This improves accessibility and exit options only if the operating model is funded and maintained. It is not defensible differentiation until storage, abuse response, delivery reliability, security operations, migration, and sustainability are resolved.

The confidentiality contract must be literal: **Standard** can support service-assisted recovery, search, and easier editing. **Sealed** should aim to keep plaintext from the service, but it requires pre-provisioned recipient keys or envelopes; guardians authorize release and cannot reconstruct a missing key. The hosted service and a self-hosted install should not promise equivalent operational security or delivery reliability.

The project should not market itself as a legal will, executor, or guaranteed proof of death. LastSignal itself explicitly disclaims being a substitute for a will or other legal instrument ([README](https://github.com/giovantenne/lastsignal#readme)); the safer niche is continuity instructions and personal communications, with clear legal boundaries. Delivering medical, credential, or estate instructions does not itself confer legal authority or satisfy jurisdiction-specific formalities.

## Limitations and follow-up questions

- No claim of exhaustiveness or uniqueness is warranted from this review.
- Repository source and README claims were not independently audited, deployed, or penetration-tested.
- Letter Vault and Afterword are especially close in claimed features but had 0 stars, no test tree identified, and unavailable linked deployments in this snapshot; they are evidence that features were claimed and portions appear in source, not evidence of production reliability.

- The `Vidha` and retired `Viraha` checks were bounded snapshots; they did not cover every code forge, domain, app store, social handle, corporate registry, common-law use, or trademark office.
- A next pass should separately test live onboarding/editor/release UX for LastSignal and Everplans, and perform a threat-model comparison before choosing any cryptographic or automatic-release design.
