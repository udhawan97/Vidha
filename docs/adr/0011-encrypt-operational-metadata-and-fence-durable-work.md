# Encrypt operational metadata and fence durable work

Vidha will encrypt classified operational metadata at the application boundary behind a replaceable key-provider and cipher port. The envelope records an opaque record identifier, schema and key version, a unique 96-bit AES-GCM initialization vector, authenticated ciphertext, retention boundary, and update time. Associated data binds the record identifier and schema version; an unknown key version, reused initialization vector, authentication failure, malformed plaintext, or context mismatch fails closed. Queryable scheduling fields remain a deliberately small, content-free plaintext surface.

Durable scheduled work and synthetic outbox intent use positive allowlists, opaque semantic keys, bounded attempts, retry and dead-letter states, expiring leases, and a monotonically increasing fencing generation. Encrypted state and outbox intent must commit atomically. A lease that has expired or been superseded cannot settle, even if a paused worker later resumes. Delivery semantics are at least once with an idempotent sink, never exactly once.

Phase 3B adds injected per-record AES-GCM data keys wrapped by an in-memory AES-KW provider, atomic persisted rewrap without ciphertext change, Ed25519-signed generation/parent backup manifests, and an external anti-rollback inventory fixture. Closure slice 2 adds a KMS-shaped wrapped-key envelope for bounded PostgreSQL custom archives, inventory advancement only after artifact persistence, exact non-current retention retirement, a dedicated non-superuser logical restore, restore-safe invariants, and immutable explicit promotion. PostgreSQL also atomically commits Plan state, append-only audit, schedule, content-free outbox intent, and claimed-job settlement. Closure slice 5 restricts the runtime worker to opaque claim/fencing input while the adapter derives database time and canonical policy-revision-bound `ADVANCE_TIME`; disposable gates exercise four execution crash boundaries, one-stage catch-up through Concern, stale-schedule rejection, retry exhaustion, dead-letter inspection, and idempotent synthetic-sink replay. This still does not prove external key custody, streaming or durable database backup, persistent-volume recovery, Standard Mode, Sealed Mode, deletion completeness, provider delivery, or production scheduling reliability.
